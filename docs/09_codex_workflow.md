# 《折光回廊》Codex 协作工作流

## 1. 当前阶段原则
本仓库当前只用于项目策划文档整理。Codex 在这个阶段的主要职责是：
- 补全文档
- 整理结构
- 细化关卡与资产表
- 记录决策与风险

当前阶段明确不做：
- 不创建 `src`
- 不创建 `package.json`
- 不安装依赖
- 不擅自生成游戏代码原型

## 2. 分支策略
- `main`：主分支，只接收已评审内容
- `docs/*`：文档分支，用于策划、需求、流程整理
- `feat/*`：未来功能实现分支
- `fix/*`：未来缺陷修复分支

当前文档初始化分支：
- `docs/initial-game-design`

## 3. 文档修改约定
1. 所有项目文档统一使用中文。
2. 如果规则定义变更，必须同步更新对应文档。
3. 不允许让多个文件出现相互矛盾的机制描述。
4. 修改关卡时，优先改 `05_level_design.md`，再联动 `02_mvp_scope.md` 与 `08_risks_and_decisions.md`。

## 4. 推荐的 Codex 任务类型

### 4.1 适合直接交给 Codex 的事
- 把房间思路扩成具体谜题步骤
- 把资产清单补成可执行表格
- 统一术语，例如门锁、感应器、滤光片命名
- 整理试玩记录并输出结论
- 生成 PR 描述草稿和提交说明

### 4.2 暂时不要直接交给 Codex 的事
- 在范围未冻结前生成代码骨架
- 未确认技术路线前创建工程结构
- 根据模糊想法直接产出新系统
- 在没有评审的情况下扩展世界观到大体量剧情

## 5. 建议的协作节奏
- 第一步：先说明要改哪份文档、为什么改。
- 第二步：让 Codex 先读现有文档，再补充或改写。
- 第三步：要求 Codex 输出“改了什么、为什么改、影响哪些文件”。
- 第四步：由人工快速过一遍关键决策是否跑偏。

## 6. 推荐提示模板

### 模板 A：细化关卡
“请基于 `docs/05_level_design.md`，把 R07 到 R09 拆成更细的玩家操作步骤、错误解法和提示文案，不要新增新机制。”

### 模板 B：整理决策
“请检查 `docs/01_game_design.md`、`docs/02_mvp_scope.md`、`docs/08_risks_and_decisions.md` 是否存在冲突，并直接修正文档。”

### 模板 C：准备评审
“请为当前文档分支生成一份 PR 说明，包含项目目标、范围边界、主要决策和待确认问题。”

## 7. Codex 输出验收标准
- 内容必须具体，不能只写抽象口号。
- 不能偷偷引入未讨论的新系统。
- 修改后文档之间术语一致。
- 所有结论都要落到文件，而不是只停留在回复里。

## 8. 从文档阶段进入实现阶段的门槛
只有满足以下条件，才允许让 Codex 开始建立代码工程：
1. `02_mvp_scope.md` 已冻结
2. `05_level_design.md` 的 12 个房间都写清楚
3. `06_asset_manifest.md` 的 P0 资产已确认
4. `08_risks_and_decisions.md` 中技术路线已确认

## 9. 提交流程建议
- 单次修改尽量围绕一个主题，例如“关卡细化”或“风险补充”。
- 提交信息要能反映修改意图，例如“docs: 细化折光回廊初版策划文档”。
- 提交前检查是否误加入代码、依赖文件或无关产物。
