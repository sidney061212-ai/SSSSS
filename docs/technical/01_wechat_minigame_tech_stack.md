# 《折光回廊》微信小游戏技术路线

## 1. 文档目标
本文用于明确《折光回廊》后续代码阶段应采用的技术栈、渲染方式、生命周期处理和性能边界，避免把一个轻量竖屏解谜小游戏做成复杂工程。

## 2. 推荐技术路线
推荐路线：
- 微信小游戏原生 Canvas 2D
- TypeScript

推荐使用 TypeScript 的原因：
- 关卡数据结构更稳定，字段命名不容易漂移。
- 能减少 AI 写代码时字段乱用、漏传和类型不一致。
- 方便后续扩展镜子类型、障碍类型、聚光点类型、出口类型。
- 在不引入重型框架的前提下，依然能保持较好的可维护性。

落地方式建议：
- 源码以 TypeScript 编写。
- 产物编译为小游戏运行所需的 JavaScript。
- 不额外引入 Web 页面层，玩法直接运行在小游戏原生画布环境中。

## 3. 渲染方式
本项目使用 Canvas 2D 绘制以下内容：
- 光线
- 镜子
- 障碍
- 聚光点
- 出口
- 基础 UI
- 发光效果

设计原则：
- 核心玩法元素优先代码绘制。
- 只把后续首页主视觉、分享卡片等包装素材作为位图资源候选。
- 玩法主画面不依赖 DOM。
- 不依赖复杂 UI 框架。
- 不使用 3D 引擎。

## 4. 微信小游戏生命周期
### 4.1 启动
- 读取小游戏入口。
- 初始化基础配置和全局常量。
- 创建主画布和 2D 上下文。

### 4.2 资源初始化
- 先加载 Prototype 0.1 必需的最小资源。
- 若资源全部代码绘制，则资源阶段只需完成配置准备和字体、音频接口预留。

### 4.3 画布初始化
- 获取屏幕尺寸、像素比和安全区信息。
- 计算逻辑分辨率到物理像素的映射关系。
- 初始化渲染器和布局信息。

### 4.4 主循环开始
- 启动固定入口的帧循环。
- 每帧只处理输入、状态更新和必要重绘。
- 光路计算不必每帧全量执行，优先按交互变化触发重算。

### 4.5 进入后台暂停
- 监听小游戏进入后台事件。
- 暂停动画、音效和帧循环中的非必要更新。
- 保留当前关卡运行时状态。

### 4.6 回到前台恢复
- 重新校验屏幕尺寸和安全区。
- 恢复帧循环。
- 必要时重新绘制当前场景。

### 4.7 屏幕尺寸变化或适配
- 当设备尺寸、旋转锁定信息或安全区变化时，重新计算布局映射。
- 关卡逻辑坐标不变，只更新渲染映射。

## 5. 包体和性能原则
- 少用大图。
- 核心玩法元素代码绘制。
- 控制粒子数量。
- 控制每帧计算量。
- 光线模拟在交互变化时重新计算，不一定每帧重复全量计算。
- 60 FPS 作为目标，但 Prototype 阶段优先正确性。

建议的性能策略：
- 关卡静态背景和底板可单独缓存。
- 选中高亮、拖动中的镜子、光线路径和 HUD 作为动态层重绘。
- 拖动时优先保证光路反馈清晰，如果真机性能不足，再退化为松手后重算。

## 6. 为什么不引入重型技术
《折光回廊》第一阶段只验证第 1 关垂直切片，当前重点是：
- 关卡看图是否清楚
- 镜子拖动与旋转是否顺手
- 光路模拟是否稳定
- 光能衰减是否形成可见优化空间

这些问题都可以用原生小游戏能力解决，因此没有必要提前增加框架复杂度。

## 7. 不引入内容
不要引入：
- Three.js
- Pixi.js，除非后续证明必要
- Matter.js
- 重型动画库
- React DOM
- WebGL 复杂管线
- 真实折射模拟
- 通用 ECS 框架

## 8. 本阶段做什么
- 确定后续实现采用微信小游戏原生 Canvas 2D。
- 确定源码优先使用 TypeScript。
- 确定生命周期、适配和性能的技术边界。

## 9. 本阶段不做什么
- 不实际搭建小游戏工程。
- 不安装 TypeScript 或任何构建依赖。
- 不引入第三方渲染库。
- 不实现生命周期代码。
