# 《折光回廊》技术架构风险

## 1. 文档目标
本文用于记录本阶段最关键的技术风险，以及对应的简化策略，确保后续代码实现时优先保证 Prototype 0.1 可验证，而不是被复杂度拖住。

## 2. 风险 1：光线反射计算复杂化
风险说明：
- 一旦追求真实光学、折射、镜面厚度或复杂材质，模拟器复杂度会迅速失控。

解决：
- 使用简化 2D 线段反射，不追求真实折射。
- Prototype 0.1 只处理单光源、单出口、普通镜子。

## 3. 风险 2：拖动和旋转交互冲突
风险说明：
- 如果拖动和旋转都依赖同一种手势，玩家会难以控制，代码也容易状态混乱。

解决：
- Prototype 0.1 使用点击步进旋转，后续再加旋转手柄。
- 通过拖动阈值区分点击与拖动。

## 4. 风险 3：Canvas 高清适配模糊
风险说明：
- 若不处理像素比，细光线和镜子边缘会发虚，直接影响可读性。

解决：
- 处理 `devicePixelRatio`，逻辑坐标和物理像素分离。
- 所有输入和渲染统一走逻辑坐标换算。

## 5. 风险 4：关卡写死导致后续难扩展
风险说明：
- 如果第 1 关直接写在渲染逻辑里，后面一扩关就需要拆结构返工。

解决：
- 从第一关开始使用 `LevelConfig` 数据驱动。
- 重置、切关、评分都从数据出发，不从场景脚本硬编码。

## 6. 风险 5：过早加入分光导致失控
风险说明：
- 多束光、多出口、多颜色会显著提高模拟、渲染和关卡设计复杂度。

解决：
- 只在文档预留，不在 Prototype 0.1 实现。
- 先把单束反射的可玩性验证清楚。

## 7. 风险 6：UI 变复杂
风险说明：
- 若首版就加入完整首页、选关页、设置页，会把注意力从玩法验证上拉走。

解决：
- 第一版直接进入 Gameplay，暂不做完整首页。
- ClearResult 只做简单覆盖层。

## 8. 风险 7：Codex 一次性写太多代码
风险说明：
- 一次性完成过多模块，容易让问题交织，审核困难，返工成本高。

解决：
- 后续代码阶段按 Task 1 到 Task 8 分支或 commit 逐步完成。
- 每个任务完成后单独验收，不跨阶段偷做功能。

## 9. 风险 8：子代理结论互相冲突
风险说明：
- 不同分析方向如果术语、状态名、边界不统一，最终文档会自相矛盾。

解决：
- 主代理统一裁剪，只保留一个明确方案。
- 统一采用“微信小游戏 + Canvas 2D + 数据驱动 + 事件驱动重算”的主线。

## 10. 补充风险：过度预留导致首版变重
风险说明：
- 如果把未来扩展字段、未来页面、未来资源管线都当成当前必做，会让 Phase 2 文档失去可执行性。

解决：
- 所有扩展只做“接口预留”，不做“当前必落地”。
- 每份文档都明确“本阶段做什么”和“本阶段不做什么”。

## 11. 风险监控清单
后续代码阶段如出现以下现象，应视为偏离方向：
- 开始讨论 3D 或物理引擎
- 开始提前实现分光聚能点
- 开始为首页包装投入大量时间
- 开始让第 1 关依赖多张位图或复杂资源
- 开始把状态机扩写成当前并不需要的巨大系统

## 12. 本阶段做什么
- 识别 Phase 2 最关键的技术风险。
- 给出 Prototype 0.1 可执行的降复杂策略。

## 13. 本阶段不做什么
- 不建立正式风险管理系统。
- 不引入额外中间件来解决还未发生的问题。
- 不为了“以后可能会用”就提前实现复杂机制。
